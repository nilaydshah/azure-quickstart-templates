🎯 Root Cause Analysis

Root Cause #1: ARM NIC RP Rate Limit
The NIC throttling (49,893 × 429s) is an inherent ARM rate limit on Microsoft.Network/networkInterfaces PUT operations. It occurs regardless of concurrent VM creation. Separating NICs into their own phase actually WORSENED throttling because:
  • In combined approach: NIC PUTs are paced by VM template dependency chains (NIC → VM)
  • In pre-NIC approach: All 5,000 NIC PUTs fire simultaneously, immediately hitting the rate limit
  • Only 4.1% of NIC PUT requests succeeded on first attempt
Root Cause #2: NIC Batch Deployment Failure
All 20 NIC ARM template batches eventually failed after ~11.5 hours due to ARM deployment timeout/retry exhaustion. 696 NICs were never created, leading to 693 VM failures in Phase 2.
Positive: VM Phase Speed
When NICs already exist, the VM creation phase completes ~4× faster (~15 min vs 63 min). This confirms that NIC-VM dependency is a significant bottleneck in the combined approach. However, the total end-to-end time is worse due to NIC pre-creation overhead.

💡 Recommendations

  1. Keep Combined Approach: The combined NIC+VM template (Run 5 approach) achieves better results (5,000 VMs in 63 min) because VM dependency chains naturally pace NIC creation and avoid hitting the ARM rate limit as hard.
  2. Investigate NIC Accelerated Networking: The NIC template has acceleratedNetworking enabled. Each NIC PUT triggers additional backend operations. Consider testing without acceleratedNetworking.
  3. ARM Rate Limit Increase: Request an ARM write rate limit increase for the subscription to reduce NIC 429s in both approaches.
  4. Smaller Concurrent Batches: Instead of 20 parallel batches, try 5-10 batches to stay under the ARM rate limit while maintaining parallelism.
