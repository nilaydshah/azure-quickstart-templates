⚠️ Failure Analysis

Why all 20 batches show "Failed"

Root Cause: OSProvisioningTimedOut

ARM template deployments fail if any VM in the batch experiences OSProvisioningTimedOut (>20 min for guest agent to report ready). Even though 4,600+ VMs succeeded, a few slow VMs per batch cause the entire 250-VM batch deployment to be marked as "Failed".

Impact: 384 VMs missing (5,000 - 4,616 = 384 VMs, 7.7%). These VMs either hit quota limits or OSProvisioningTimedOut before creation.

Key Observations

  • DiskRP: Zero failures across 69,287 operations — disk allocation is not the bottleneck
  • XStore creation ops (CreateContainer, CreateAsync, WritePagesAsync): 100% success — storage layer is healthy
  • XStore cleanup ops (DeleteCorLink, DeleteContainer): 92-98% success — cleanup path has retries, not blocking
  • SRP: Zero throttling — no 429 or 503 errors during the test
  • Peak XStore load: ~325 ops/VM (1.5M total / 4,616 VMs) — higher than Run 2's 185 ops/VM

📋 Action Items & Recommendations

🔴 Critical

  1. Investigate missing 384 VMs — Determine if OperationNotAllowed (quota) or OSProvisioningTimedOut was the cause for each undeployed VM
  2. XStore FetchInternalProperties 5.6% failure — 9,049 failures (was 3.5% in Run 1). Regression under higher load? Check if these are transient 404s vs actual errors
  3. XStore DeleteCorLink 7.3% failure — 7,495 failures with P99 of 1.2s. Check if CorLink cleanup queue is overloaded

🟡 Improvements

  2. ARM template error handling — Change deployment mode to continue on individual VM failures instead of failing the batch

  4. Add VM provisioning timeout extension — Consider increasing OS provisioning timeout from 20min to 30min for scale scenarios
