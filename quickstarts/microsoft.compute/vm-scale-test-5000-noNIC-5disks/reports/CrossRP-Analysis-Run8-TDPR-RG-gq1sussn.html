5. Three-Layer Pool Hit/Miss Analysis

Azure VM provisioning involves three distinct pool/preallocation layers, each managed by a different resource provider. Understanding pool hit rates at each level is critical for scale test performance optimization. A "pool hit" means the RP reused a pre-allocated resource (fast path); a "pool miss" means it had to create from scratch (slow path).

5.1 CRP Pool — Preprovisioned VM Reuse (Disk Preallocation)

CRP maintains a pool of preprovisioned VMs with pre-allocated OS disks. When a VM PUT arrives, CRP checks if a preprovisioned VM can be reused. Tracked via labels.PreprovisionedVMReuse in ApiQosEvent_nonGet.

5.2 DiskRP Pool — Storage Account Allocation (PoolManager)

DiskRP maintains a pool of pre-created storage accounts for managed disks. When a disk needs a storage account, StorageAccountAllocatorBlock first checks the pool. If available (sync allocation), the disk is placed on an existing account. If the pool is exhausted, TryAllocateStorageAccountActionBaseAsync triggers creation of a new storage account (which involves ARM → SRP → DNS registration). Tracked via DiskRPExternalComponentQoSEvent with componentName=PoolManager_*.

Reason: Managed disk storage accounts are created in Microsoft's internal platform subscription, not in the user's subscription (b883903d-...). SRP telemetry (RegionalSRP_ServiceApiQosEvent) is keyed by the storage account's owning subscription ID, which is a Microsoft-managed subscription.

SRP Data Path Explanation

Why SRP has zero direct rows:
  1. PremiumV2_LRS data disks use DirectDriveGateway, which bypasses traditional SRP/XStore entirely.
  2. StandardSSD_LRS OS disks use XStore storage accounts, but these accounts are created in Microsoft's internal managed-disk subscription — not in the user subscription (b883903d-...).
  3. SRP telemetry (RegionalSRP_ServiceApiQosEvent) is keyed by the owning subscription of the storage account, which is Microsoft-managed and not queryable with user subscription filters.

Observable SRP impact: The DiskRP TryAllocateStorageAccountActionBaseAsync duration (avg 33.9s) includes the full ARM→SRP→DNS registration pipeline for new storage accounts.

10. Key Findings & Recommendations

✅ What Worked Well

  • NoNIC approach: Zero NIC 429 errors (vs 24K-50K in prior runs)
  • DiskRP Storage Account Pool: 98.2% hit rate, excellent pool management
  • Disk creation latency: P50=0ms, P90=15ms — near-instant when quota allows
  • DirectDriveGateway: 100% success on PatchDisk (24K ops), no SRP dependency
  • PoolManager load distribution: 5 managers handling load evenly
  • Inline NIC throughput: NRP FastPath enabled on all VMs

⚠ Issues & Bottlenecks

  • PremiumV2DiskCount quota (20K): Hard limit — 5K VMs × 4 disks = exactly at limit, race condition causes partial failures
  • CRP pool exhaustion: Only 33.2% hit rate at 5K burst — pool refill can't keep up
  • ArmRegistrationBlock P99=183s: ARM throttling creates extreme tail latency in disk registration
  • Retry amplification: 6,465 CRP PUTs for 5,000 target VMs (29% retry overhead)
  • New storage account creation: 33.9s avg when pool miss occurs (SRP DNS is in this path)

Recommendations for Next Run
